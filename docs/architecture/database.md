# Database architecture

**Status:** conceptual proposal, except the audit section. Read [ADR-003](../decisions/ADR-003-inventory-and-transaction-boundaries.md), [glossary](../../CONTEXT.md) and [lifecycle](transaction-lifecycle.md). Add tables in the issue that first uses them, not in one speculative master migration.

## What exists and what to retain

`src/lib/db/schema.ts` defines only `seller_waitlist` and `brand_waitlist`. Both have UUID primary keys, required name/email fields, optional plain-text lead qualifiers, and `timestamptz created_at`. `drizzle/0000_clammy_ma_gnuci.sql` creates them; `0001_many_vector.sql` enables RLS and revokes all table privileges from `anon` and `authenticated`. The journal and snapshots agree with both migrations. There are no domain tables, foreign keys, secondary indexes, RLS policies or financial records. The absence of client policies is deliberate: waitlist leads have no direct browser database path.

Keep these lead tables outside the marketplace model. Their free-text category answers must not become an inventory enum. Keep generated migration history intact. PR #2 reports applying migration 0000 to its development database; this audit did not inspect any database or prove application in other environments.

The server builds a `postgres()` client with `prepare: false`, wrapped by Drizzle and exposed as `getDb()`. The module imports `server-only`, so Next.js rejects a client module that imports it. Since FOUNDATION-002 the client is created on first use rather than at import, and `DATABASE_URL` is validated there: `next build` imports the waitlist route while collecting page data, so a static-only build must not require a database, while a missing or malformed value fails at the first query with the variable named. No Supabase browser client exists. Disabling prepared statements is consistent with transaction-pooler constraints, but the actual connection mode, role, TLS, pool size and deployment lifetime remain unverified. [Supabase connection guidance](https://supabase.com/docs/guides/database/connecting-to-postgres).

**Implemented correction:** migration 0001 establishes deny-by-default access for the two lead tables with RLS plus explicit client-role revokes. `tests/db/waitlist-access.sql` and its Docker runner assert effective CRUD denial for `anon` and `authenticated`, preservation of pre-migration rows, and inserts through a narrowly granted disposable `BYPASSRLS` server role. The runner also posts representative seller and brand payloads through the real Next.js route. This proves repository behavior on disposable PostgreSQL, not which migrations, schemas, grants or connection role are deployed. [Supabase RLS guidance](https://supabase.com/docs/guides/database/postgres/row-level-security).

## Proposed entities

All rows use stable IDs, timestamps and explicit owner/actor references where relevant. Money uses integer minor units with currency; financial and contractual records are retained rather than cascade-deleted. UUID domain keys are preferred; Better Auth key types must be selected and matched before dependent foreign keys are generated. The table names below are conceptual contracts, not a claim that a particular library generates these exact names.

## Constraints across entities

Prefer foreign keys, unique/check constraints and narrowly scoped transactions for durable invariants. Cross-table ownership is enforced by a single domain operation plus integration tests; use composite keys where this materially prevents mismatched template/seller references. Index foreign keys and actual access paths: listings by page/status, offers by recipient/state/expiry, reservations by spot/period, orders by participant/status, pending provider events and payout failures. Do not add speculative search indexes.

Use UTC `timestamptz` for instants and preserve the IANA timezone for display. Occupancy uses half-open intervals `[start,end)` including agreed application/removal buffers. Adjacent bookings may touch only if the production policy allows it. A date-only event is converted once using the explicit timezone; never infer it from a browser locale.

Reservation invariant: an active `held` or `confirmed` row cannot overlap another for the same physical conflict key. Prefer a PostgreSQL exclusion constraint with a timestamp range and equality key (verify extension availability with Supabase), or serialize all changes by locking the stable inventory-spot row and checking overlaps inside the transaction. Choose and record the concrete approach in ORDER-001. A separate unique listing ID or a “check then insert” outside a lock is insufficient. Expired holds must be transitioned to released under the same lock before granting new capacity; a clock-dependent partial index is unsuitable.

At offer acceptance, lock current offer revision and inventory, recheck listing version, eligibility, production lead time, expiry and amount, create order snapshot/reservation/activity atomically, and supersede/close competing proposal states as needed. Provider calls happen after commit through a durable operation record; never hold a DB transaction open over checkout/network calls.

Transactions/events are idempotent at business level. Provider-specific idempotency is helpful but cannot be assumed for every endpoint. Snapshot actual fee amount, basis/rate version, tax and cost responsibilities; changing the platform fee only affects future agreements. Refund, transfer reversal and bank-settlement reversal each have their own operation evidence.

## Access, retention and migrations

Better Auth is not Supabase Auth; its session user does not automatically populate `auth.uid()` or a PostgREST JWT. The intended path is browser → Next.js authorized operation → Drizzle → Postgres, with no public Data API access to private tables. Prove role grants/RLS and explicit server owner checks; never assume hiding a button or adding proxy redirects secures an operation.

For the current waitlist route, `DATABASE_URL` must identify a server-only role that can insert and bypass RLS (the table owner, a superuser, or a narrowly granted `BYPASSRLS` role). That bypass is infrastructure authority, not end-user authorization, and its credentials must never enter the browser. FOUNDATION-002 implemented that boundary in the repository: `src/lib/env/server.ts` is the only module that reads the connection string and is marked `server-only`, `src/lib/env/database-url.ts` validates the scheme and host without ever echoing the value into an error, and `pnpm test:client-boundary` asserts both that module and `src/lib/db` are rejected in a client bundle. Which role a deployment actually uses remains operator-verified.

Use separate app and migration credentials where the runtime supports it. `drizzle.config.ts` reads `DATABASE_MIGRATION_URL` when it is set and falls back to `DATABASE_URL`, so the split is available without a code change and optional where a managed instance exposes only one role. Migration owner may create schema; app role has only required runtime permissions; clients have no direct grants to lead, auth, financial or proof data. The per-connection privileges expected today are tabulated in [setup](../development/setup.md#database-connections-and-roles). Document any RLS bypass for the server role and test ownership in application operations. Do not use production credentials to run development, tests or previews.

Drizzle generates new reviewed migrations and metadata. Review SQL for grants, constraints and data preservation, apply to disposable DB and verify expected drift; never modify applied 0000. One agent owns the migration sequence, including auth-generated tables. Fresh install and upgrade paths both need tests. Production migration/backup/restore procedures and retention periods require explicit environment ownership before live launch. Legal retention of orders/financial evidence can outlast account deletion; redact public profile data while preserving required records, with founder-approved policy.

## Deferred schema

No custom balance ledger, wallet, escrow, auction bids, recommendation features, product-category enum, multi-seller order lines, recurring availability engine or normalized location/event/social graph. Reconciliation records describe provider movements and amounts owed; they are not spendable customer balances. Introduce a settlement allocation join only if the selected provider exposes batch bank settlements; that is a real financial constraint, not speculative marketplace infrastructure.
